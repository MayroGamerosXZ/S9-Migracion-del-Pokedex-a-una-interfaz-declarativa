0 Introducción — ¿De dónde venimos?

"Antes de ver el código nuevo, es importante entender el punto de partida. La Pokédex original estaba escrita en Vanilla JavaScript y constaba de tres archivos: pokemon.html, pokemon.css y pokemon.js. Toda la lógica vivía en un solo archivo de 193 líneas, usando document.createElement e innerHTML para pintar las tarjetas manualmente en el DOM. Funciona, pero es difícil de mantener, probar y escalar. El objetivo de esta sesión es ver cómo migramos eso a una arquitectura moderna con React y TypeScript, donde la interfaz se describe en vez de ser construida pieza a pieza."

Concepto clave: "Imperativo" (dile al navegador cómo hacerlo) vs. Declarativo (dile al navegador qué mostrar y React se encarga del resto).

1 Arquitectura del Proyecto

"La primera decisión fue crear el proyecto con Vite, que es una herramienta de construcción moderna. El comando npm create vite@latest pokedex-react -- --template react-ts nos generó la base. Luego organizamos el código en carpetas con responsabilidades claras siguiendo el principio de separación de capas."

Estructura de carpetas · D:\pokedex-react\src\ 
src/
├── types/
│   └── pokemon.ts         ← Contratos de datos (interfaces)
│
├── services/
│   └── pokeApi.ts         ← Capa de acceso a la API (fetch)
│
├── components/
│   ├── SearchForm.tsx     ← Formulario controlado + debounce
│   ├── RequestStatus.tsx  ← Guarda de estados de la UI
│   ├── PokemonList.tsx    ← Iterador de tarjetas
│   └── PokemonCard.tsx    ← Tarjeta individual
│
├── App.tsx                ← Orquestador principal (estado global)
├── main.tsx               ← Punto de entrada (monta React en el DOM)
└── index.css              ← Estilos globales + colores por tipo
¿Por qué separar así? Si mañana la PokéAPI cambia su URL, solo tocamos pokeApi.ts. Si queremos cambiar la tarjeta, solo tocamos PokemonCard.tsx. Nadie afecta a nadie.

2 Tipos TypeScript · src/types/pokemon.ts

"TypeScript nos exige definir la forma de los datos antes de usarlos. Este archivo es el contrato de toda la aplicación. Si la API nos manda un campo que no esperamos, TypeScript nos avisa antes de que lleguemos al navegador. Aquí definimos tres categorías: los datos del Pokémon, las respuestas de la lista paginada, y los posibles estados de la UI."

src/types/pokemon.ts — fragmento clave 
// 1. Describe cómo llegan los tipos del Pokémon desde la API
export interface PokemonType {
  slot: number;
  type: { name: string; url: string; };
}

// 2. Describe el objeto completo de un Pokémon
export interface Pokemon {
  id:      number;
  name:    string;
  weight:  number;
  types:   PokemonType[];
  stats:   PokemonStat[];
  sprites: PokemonSprites;
  cries?:  PokemonCries;  // el ? indica que puede no existir
}

// 3. Los cinco estados posibles de la UI (unión de literales)
export type RequestState =
  'idle' | 'loading' | 'success' | 'empty' | 'error';
¿Por qué RequestState como unión de literales? Porque TypeScript nos impedirá asignar cualquier otro string que no esté en la lista. Si escribimos 'cargando' en vez de 'loading', el compilador rompe antes de que el código llegue al navegador.

3 Servicio PokéAPI · src/services/pokeApi.ts

"Este archivo es la única parte de la aplicación que sabe que existe una API externa. Los componentes nunca hacen un fetch directamente; siempre le piden los datos a este módulo. 4 SearchForm · src/components/SearchForm.tsx

"Este componente es el formulario de búsqueda. Tiene dos responsabilidades: primero, ser un formulario controlado, es decir, React es quien guarda el valor del input en su estado y no el DOM. Segundo, implementar un debounce para que la búsqueda no dispare una petición por cada letra que escribimos, sino que espere 400 milisegundos de silencio antes de actuar."

src/components/SearchForm.tsx — las dos piezas clave 
// ── PIEZA 1: Formulario Controlado ──────────────────────────────
// El valor del input viene de React (value={searchTerm})
// React se entera de cada cambio via onChange
<input
  value={searchTerm}                        // ← React controla lo que se ve
  onChange={e => setSearchTerm(e.target.value)} // ← React controla los cambios
  list="pokemon-suggestions"                 // ← conectado al datalist
/>

// ── PIEZA 2: Debounce con useEffect ─────────────────────────────
// Se ejecuta cada vez que searchTerm cambia
useEffect(() => {
  const timer = setTimeout(() => {
    onSearch(searchTerm);     // ← dispara búsqueda al terminar
  }, 400);                    // ← 400ms de espera

  return () => clearTimeout(timer); // ← cancela si el usuario sigue escribiendo
}, [searchTerm]);              // ← se reinicia con cada letra
¿Qué pasaría sin debounce? Si escribimos "pikachu" (7 letras), se lanzarían 7 peticiones a la API: "p", "pi", "pik"... Con debounce solo se lanza 1, cuando el usuario termina de escribir.

5 RequestStatus · src/components/RequestStatus.tsx

"Este componente es como un guardia de tráfico. Recibe el estado actual (loading, error, empty) y decide qué mostrar. Si está cargando, muestra 20 tarjetas esqueleto animadas. Si hay error, muestra un mensaje comprensible. Si no hay resultados, muestra el estado vacío. Si todo está bien, simplemente deja pasar a sus hijos (la lista de Pokémon). Los componentes padres no tienen que preocuparse por ninguno de esos casos."

src/components/RequestStatus.tsx — lógica de guardas 
// Si está cargando → 20 tarjetas "skeleton" animadas
if (state === 'loading' && !children) {
  return (
    <section className="dex">
      {Array.from({ length: loadingCount }).map((_, i) => (
        <article key={i} className="pokemon-card pokemon-card--skeleton"/>
      ))}
    </section>
  );
}

// Si hubo error → mensaje descriptivo al usuario
if (state === 'error') { return ( <p>{errorMessage}</p> ); }

// Si no encontró nada → estado vacío
if (state === 'empty') { return ( <p>Sin resultados</p> ); }

// Si todo está bien → renderiza los hijos normalmente
return <>{children}</>;

7 App.tsx — El Orquestador

"App.tsx es el cerebro. Es el único componente que habla con el servicio de la API y el único que mantiene el estado global. Tiene cinco variables de estado y el concepto más sofisticado del proyecto: el AbortController. Cada vez que se lanza una nueva petición, se cancela la anterior usando una referencia mutable con useRef. La clave está en el bloque catch que detecta si el error es una cancelación esperada y simplemente lo ignora, sin mostrar ningún error al usuario."

src/App.tsx — AbortController y manejo de estados 
// Una referencia mutable que NO provoca re-renders cuando cambia
const abortControllerRef = useRef<AbortController | null>(null);

const loadPokemons = useCallback(async (offset) => {

  // 1. Si hay una petición en vuelo → cancelarla
  if (abortControllerRef.current) {
    abortControllerRef.current.abort();
  }
  // 2. Crear nueva señal para esta petición
  abortControllerRef.current = new AbortController();
  const { signal } = abortControllerRef.current;

  try {
    const data = await fetchPokemonList(LIMIT, offset, signal);
    setPokemons(data);
    setRequestState('success');
  } catch (error: any) {
    // 3. Si fue cancelación → ignorar silenciosamente
    if (error.name === 'AbortError') return;
    // 4. Si fue error real → mostrar al usuario
    setRequestState('error');
  }
}, []);
¿Por qué useRef y no useState? Porque si usáramos useState para guardar el AbortController, React re-renderizaría el componente cada vez que se crea un nuevo controlador. Con useRef guardamos el valor sin disparar renders.

8 Flujo Completo de una Búsqueda

"Para cerrar la arquitectura, veamos el camino completo que recorre un dato desde que el usuario escribe hasta que aparece la tarjeta en pantalla."

Usuario escribe "pika" → SearchForm (onChange) → ⏱ Debounce 400ms
↓
onSearch("pikachu") → App: AbortController.abort() petición anterior
↓
setRequestState('loading') → RequestStatus muestra Skeletons
↓
pokeApi.fetchPokemonDetails("pikachu") → fetch a pokeapi.co
↓ (respuesta JSON)
setPokemons([pikachu]) → setRequestState('success')
↓
RequestStatus deja pasar → PokemonList → PokemonCard

Sin Duplicados (Cargar Más)

En la lista principal, hacer click en "Cargar más" varias veces rápidamente. Luego inspeccionar el DOM.
